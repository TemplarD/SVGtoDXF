### **Структурированное Техническое Задание для LLM-агента (SWE 1.5)**

**Проект:** SVG2DXF Converter
**Цель:** Разработать кроссплатформенное настольное приложение с GUI для конвертации SVG в DXF на языке Rust.
**Ключевой принцип:** **Модульность, тестируемость и централизованное логирование/отладка.** Все компоненты должны быть изолированы, иметь четкие интерфейсы и поддаваться как модульному, так и интеграционному тестированию, в том числе автоматическому силами ИИ.

---

### **1. Архитектура и Технологический Стек**

#### **1.1. Бекенд (Rust Core)**
*   **Язык:** Rust 2021 edition, stable toolchain.
*   **Фреймворк GUI:** **Tauri 2.0**. Основной выбор для кроссплатформенного Rust + WebView приложения. Позволяет использовать любой frontend фреймворк.
*   **Frontend Framework:** **Yew** (с `wasm-bindgen`) **ИЛИ Leptos**. Выбор обоснован:
    *   Написание UI на Rust, что обеспечивает единую кодобазу, лучшую типобезопасность и интеграцию с бекендом.
    *   Прямой доступ к DOM и событиям, что критично для детального тестирования UI силами ИИ.
    *   Если выбран Leptos, использовать `leptos_tauri` для интеграции.
*   **Конвертация SVG -> DXF:**
    *   **Парсинг SVG:** `usvg` (быстрая и надежная библиотека для растеризации и парсинга). Альтернатива: `resvg` (на основе `usvg`).
    *   **Генерация DXF:** `dxf` crate. Позволяет программно создавать и записывать DXF файлы. **Задача:** Трансформировать дерево `usvg` в сущности DXF (LAYER, LINE, LWPOLYLINE, CIRCLE, ARC, SPLINE?).
    *   **Альтернативный путь (если `dxf` недостаточно):** Генерация DXF напрямую через написание текста по спецификации, либо использование `lyon` для тесселяции кривых в полилинии и последующей записи через `dxf`.
*   **Работа с файловой системой:**
    *   Через `tauri::api::dialog` для диалогов выбора.
    *   `std::fs`, `std::path` для операций с файлами. Обязательно использовать `fs::canonicalize` и проверки прав доступа (`fs::metadata`).
    *   Для кроссплатформенных путей - `std::path::PathBuf`.

#### **1.2. Фронтенд (WebView)**
*   **Стилизация:** Современный CSS с переменными (CSS Custom Properties) для темизации. Использовать `flexbox`/`grid`. Закругленные углы (`border-radius`), плавные переходы (`transition`).
*   **Иконки и Анимации:** Библиотека иконок (например, `Phosphor Icons` или `FontAwesome` через CDN). Анимации статусов - через CSS (`@keyframes`, `animation`).
*   **Структура UI:** Компонентный подход, предоставляемый выбранным фреймворком (Yew/Leptos).

#### **1.3. Система Логирования и Отладки (Central Debug & Test System - CDTS)**
*   **Библиотека логирования:** `tracing` + `tracing-subscriber`. Мощнее и гибче, чем `log`. Позволяет структурировать логи, добавлять поля (`span`), фильтровать по уровням.
*   **Appenders (Куда пишем):**
    *   **Файл:** По умолчанию `~/svg2dxf_converter/logs/app.log`. Ротация логов через `tracing-appender`.
    *   **In-App Debug Console:** Специальный виджет в UI, доступный по F12. Логи туда направляются через канал (например, `tokio::sync::broadcast` или `flume`) из подписчика `tracing`.
    *   **Stdout:** Только в дебаг-режиме с флагом `RUST_LOG=debug`.
*   **Режим Дебага:**
    *   Активация: Горячая клавиша **F12** (глобальный хук через `tauri-plugin-global-shortcut`) **ИЛИ** аргумент командной строки `--debug`.
    *   При активации:
        1.  Уровень логирования повышается до `trace`/`debug`.
        2.  В UI появляется плавающая/закрепленная панель **Debug Console**.
        3.  В панель начинает стримиться детальная информация, как указано в ТЗ.
        4.  Становится доступна кнопка **"Run Full Test Suite"**.
    *   **Динамическое изменение пути логов:** В дебаг-режиме в UI должна быть опция "Change Log Directory", открывающая диалог выбора папки (`tauri::api::dialog`). Новый путь применяется к `tracing_appender` для файлового вывода.
*   **Структура логов:** Каждое сообщение должно содержать:
    *   Timestamp
    *   Уровень (ERROR, WARN, INFO, DEBUG, TRACE)
    *   Цель (target) - имя модуля/компонента.
    *   Сообщение
    *   Для ошибок - полная цепочка (`error.chain()`) и, по возможности, `backtrace` (активируется флагом `RUST_BACKTRACE=1` в дебаг-режиме).

### **3. Детали Реализации Ключевых Функций**

#### **3.1. Конвертация**
*   **Процесс:**
    1.  `core::converter::load_svg(path)` -> `usvg::Tree`.
    2.  Обход дерева `usvg`. Преобразование элементов:
        *   `<path>` с `d="..."` -> Анализ команд (M, L, C, Q, A, Z). Конвертация кривых Безье и дуг в последовательности коротких отрезков (`LWPOLYLINE`) или, если библиотека поддерживает, в `SPLINE`.
        *   `<line>`, `<rect>`, `<circle>`, `<ellipse>` -> соответствующие примитивы DXF.
        *   `<text>` -> **Ограничение:** Преобразование в кривые (outlines) на стороне SVG или игнорирование с предупреждением в лог.
    3.  Сборка DXF-документа через `dxf` crate.
    4.  Запись в файл.
*   **Обработка ошибок:** Любая ошибка парсинга/конвертации на отдельном файле не должна падать всё приложение. Файл помечается статусом "Ошибка", детали пишутся в лог и отображаются в UI при наведении на иконку статуса.

#### **3.2. UI/UX**
*   **Список файлов:** Компонент `FileList`. Каждый `FileItem` содержит: имя, путь, статус (с иконкой), прогресс-бар (для "конвертации"). Состояния: `Pending`, `Converting(progress)`, `Completed`, `Failed(error)`.
*   **Выбор папки/файлов:** Команды Tauri `dialog::open(...)` возвращают пути, которые добавляются в глобальное состояние (`ui::state::AppState`), управляемое через реактивную систему фреймворка.
*   **Сохранение:** Логика `save_converted_file(original_path, dxf_data)`:
    1.  Определить целевую папку: `orig_dir = original_path.parent()`.
    2.  Проверить права на запись в `orig_dir` (`fs::metadata(orig_dir).permissions().readonly()`).
    3.  Если доступно, сохранить рядом.
    4.  Если нет, показать **один раз** за сессию диалог выбора резервной папки. Запомнить ее в состоянии для последующих файлов с той же проблемой.
*   **Справка:** Кнопка "Help" открывает модальное окно или страницу с Markdown-текстом, загружаемым из ресурсов приложения.

#### **3.3. Центральная Система Автотестирования (Integration Tests)**
*   **Цель:** Позволить ИИ (или разработчику) запускать сквозные тесты, имитирующие действия пользователя и проверяющие состояние системы.
*   **Реализация:**
    *   Использовать `wasm-bindgen-test` для тестов, взаимодействующих с UI (если выбран Yew).
    *   Для симуляции событий DOM: `web_sys::MouseEvent`, `KeyboardEvent`.
    *   Для проверки DOM: `web_sys::Document`, `Element`, методы `query_selector`, `inner_html`, `get_attribute`.
    *   **Модульность:** Каждый тестовый файл (`ui_tests.rs`) должен экспортировать набор функций (например, `test_open_file_dialog()`, `test_conversion_button_state()`), которые можно вызывать по отдельности.
*   **Запуск из Дебаг-режима:**
    1.  В панели Debug Console есть кнопка **"Run All Tests"**.
    2.  По нажатию UI вызывает Tauri-команду `run_integration_tests(test_filter: Option<String>)`.
    3.  Бекенд (в `tauri_app/src/debug.rs`) запускает тестовый раннер (`integration_tests::test_runner::run()`).
    4.  Раннер динамически (через `libtest` или собственный код) исполняет выбранные тесты.
    5.  **Логи и результаты** тестов направляются обратно в **Debug Console** через тот же канал `tracing`, что и обычные логи. Каждое утверждение (`assert!`) и результат теста логируется.
*   **План автотестирования (документ `TEST_PLAN.md`):**
    *   **Unit:** Тесты `core` на корректность парсинга и генерации.
    *   **Integration (UI):**
        1.  Открытие главного окна.
        2.  Клик по "Выбрать файлы" -> появление диалога (может мокаться).
        3.  Добавление тестового SVG -> появление записи в списке со статусом "Добавлен".
        4.  Клик по "Конвертировать" -> проверка смены статуса на "Конвертация", затем на "Завершено".
        5.  Проверка наличия выходного DXF файла в ожидаемом месте.
        6.  Тест на ошибку (битый SVG) -> статус "Ошибка".
        7.  Тест на папку только для чтения -> вызов диалога выбора альтернативной папки.
    *   **Integration (System):** Тесты на доступность файловой системы, корректность работы с путями.
    *   **Дебаг:** Тест на открытие панели по F12, на поток логов в нее.

### **4. Сборка и Распространение**

*   **Сборка под все ОС:** Использовать `tauri build` с настройками в `tauri.conf.json`. Для Linux: сборка `.deb`, `.AppImage`. Для macOS: `.dmg`. Для Windows: `.msi`.
*   **Папка `releases/`:** Создавать автоматически CI/CD (GitHub Actions). Вручную: `tauri build --target universal-apple-darwin` и т.д. Результаты складывать в `releases/{version}/`.
*   **Ведение CHANGELOG:** Следовать стандарту **Keep a Changelog**. Каждая фича, багфикс, изменение в API должно отражаться. LLM должен получать инструкцию обновлять этот файл при каждом значимом коммите.

### **5. Инструкция для LLM (SWE 1.5)**

1.  **Инициализация:** Создать workspace, описанное в п.2. Настроить `Cargo.toml` файлы с зависимостями.
2.  **Разработка:** Начинать с модуля `core` и его модульных тестов. Затем `ui` с простым макетом. Потом интегрировать через `tauri_app`. **Реализовывать систему логирования `tracing` и дебаг-панель параллельно с основными функциями.**
3.  **Тестирование:** После реализации каждой фичи (кнопка, диалог, конвертация) **немедленно** писать соответствующий интеграционный тест в `integration_tests`. Тесты должны быть **автономными** и **воспроизводимыми**.
4.  **Отладка:** Все ошибки и важные действия логировать через `tracing`. Убедиться, что в дебаг-режиме логи попадают и в файл, и в UI-консоль.
5.  **Сборка:** На каждом этапе проверять, что `tauri build` работает для текущей платформы. Финализировать сборку под все ОС в самом конце.
6.  **Документация:** Вести `CHANGELOG.md` и `TEST_PLAN.md` в процессе работы. Комментарии в коде обязательны для сложной логики.

**Главный фокус для ИИ:** Модуль `integration_tests` - это его основной инструмент для проверки своей работы. Любое изменение UI или логики должно быть покрыто вызовом соответствующих тестовых функций, которые ИИ может запускать и анализировать по логам в Debug Console.
